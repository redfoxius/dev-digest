## Architectural Constraints
- Routes → service → repository, one-way (`onion-architecture` skill; mirrors `server/src/modules/blast/{routes,service}.ts` — no `repository.ts` even needed there since blast has no DB writes of its own, but onboarding does, so it needs one).
- `service.ts` must never import `drizzle-orm` or `fastify` types — only `repository.ts` touches the `onboarding` table's Drizzle schema (`onion-architecture` skill, "Anti-Patterns" section).
- No new port/adapter is needed: composition is entirely over already-exposed `Container` getters (`container.repoIntel`, `container.llm`, `container.reposRepo`) — mirrors `server/src/modules/blast/service.ts:16-17`'s "thin composition over `Container`" shape exactly. Do **not** add anything to `platform/container.ts`.
- `OnboardingService` is constructed directly in `routes.ts` (`new OnboardingService(container)`), not exposed as a `Container` getter — matches `blast/routes.ts:20` (`const service = new BlastService(container)`), not the container-getter pattern used for cross-module shared repos.
- Fastify routes validate `params`/`querystring`/`body` via zod schemas before the handler runs (`server/AGENTS.md:30-31`); a 422 for bad input is automatic, never hand-rolled.
- A DB-backed test file must end `*.it.test.ts` or the unit/integration split silently miscounts it (`server/AGENTS.md:33`).
- `@devdigest/shared` is hand-copied, not linked — `OnboardingTourResponse` must be added to **both** `server/src/vendor/shared/contracts/knowledge.ts` and `client/src/vendor/shared/contracts/knowledge.ts` in the same change (root `AGENTS.md:30-33`; `server/INSIGHTS.md` 2026-07-27 entry documents exactly this drift class already happening once).
- Migrations are manual (`pnpm db:migrate`), never on boot (root `AGENTS.md:34`).
- Client: route-colocated `_components/`, one hook file per API domain in `lib/hooks/`, `lib/api.ts` is the only fetch boundary (`frontend-ui-architecture` skill; `client/AGENTS.md:17-22`).

## Relevant INSIGHTS.md Gotchas
- A single-table, pure `ADD COLUMN` migration (even multi-column) generates cleanly via `pnpm db:generate` with **no** interactive prompt — only a same-diff add+drop/rename triggers the disambiguation prompt that can hang non-interactively. This migration (7 new nullable columns, one table) is squarely the safe case. (`server/INSIGHTS.md`, 2026-08-07/2026-08-09 entries)
- `FEATURE_MODELS` slots have shipped with wrong (non-cheap) defaults before (`conventions`, `review_intent`, and still-unfixed `risk_brief`/`conformance`) — **already checked**: `onboarding`'s entry is correctly `openrouter`/`deepseek/deepseek-v4-flash`, no fix needed here. (`server/INSIGHTS.md`, 2026-08-07/2026-08-09 entries)
- Adding a required/new-shape field to a shared contract touched by test fixtures breaks `pnpm typecheck` only if you run it against the whole package — `server/test/**` itself is never type-checked (only transpiled), so a new `OnboardingTourResponse`-typed literal in a test needs a manual check, not just a clean `tsc`. (`server/INSIGHTS.md`, 2026-08-04 entry, `server/tsconfig.json:26`)
- `.optional()` on a field destined for LLM structured output should be treated as wrong until proven otherwise on this codebase — use `.nullish()` for any optional field in the model's own structured-output schema (this feature's per-section `diagram` especially), matching `Risk`/every other optional field in `findings.ts`/`intent/service.ts`'s own `IntentDerivation`. (`server/INSIGHTS.md`, 2026-08-14 entry)
- A new backend module needing a `RepoIntel` capability should check the facade (`repo-intel/types.ts`) before assuming a gap — this feature needs nothing new; every method it needs (`getRepoMap`/`getTopFilesByRank`/`getCriticalPaths`/`getFileEdges`/`getCallerSignatures`/`getFileContent`/`getIndexState`) is already public on the port. (`server/INSIGHTS.md`, 2026-08-14 entry re: `getFileEdges` being added as a real gap once — the counter-example confirming this module has no equivalent gap)
- Client tests in this repo mock `fetch` directly — **not** MSW, despite the `react-testing-library` skill's generic "MSW preferred" guidance. Follow `client/AGENTS.md:31` and existing `lib/hooks/*.test.ts`/page test conventions, not the skill's default. (`client/AGENTS.md:31`)
- A `useQuery` destructure that drops `isError` silently degrades an error state into the empty-state copy — always destructure `data, isLoading, isError, error, refetch` together, copying `conventions/page.tsx:41`'s full shape. (`client/INSIGHTS.md`, 2026-08-06 entry)
- `messages/en/<feature>.json` is auto-discovered by filename with no registration step — `onboarding.json` already exists with several matching keys (title/regenerate/generate/loadError); check it before writing new copy, and don't assume a missing key means the whole namespace needs scaffolding. (`client/INSIGHTS.md`, 2026-08-07 entry; `client/messages/en/onboarding.json`)
- Any absolutely-positioned popover/overlay this page adds (e.g. a stale banner or share-link toast) inside a card with `overflow: hidden` needs a manual screenshot check — RTL/jsdom has no layout engine and won't catch clipping. (`client/INSIGHTS.md`, 2026-08-05 entry)
