## Context

An eval/regression harness for reviewer agents. Every finding a user accepted/dismissed becomes a persisted `eval_cases` row (`must_find`/`must_not_flag` expectation). Running an agent against its case set (`POST /agents/:id/eval-runs`) reuses `reviewer-core`'s `reviewPullRequest` directly (never the server's `ReviewRunExecutor`), scores results with zero LLM calls, and exposes run history + a two-run compare view. `eval_cases`/`eval_runs` (`server/src/db/schema/eval.ts:7-35`) and every core contract except one (`EvalCaseInput`, `EvalRun`, `EvalRunRecord`, `EvalPerTrace`, `EvalTrendPoint`, `EvalDashboard`, `EvalCase`, `EvalOwnerKind` — `server/src/vendor/shared/contracts/eval-ci.ts`, `knowledge.ts:64-98`) already exist, shipped empty/unused. The only new type is `EvalExpectation` (§10).

Confirmed by direct inspection before planning:
- `reviewPullRequest` (`reviewer-core/src/review/run.ts:141-293`) takes `{systemPrompt, model, diff: UnifiedDiff, llm, strategy?, skills?, task?, sessionId?, onEvent?, checkCancelled?, ...}` and returns `{review, grounding, dropped, tokensIn, tokensOut, costUsd, ...}` — `review.findings` is already post-grounding *and* post-scope-filter (scope filtering only softens severity, never drops, `run.ts:264-275`), so it is exactly the "actual findings" set AC-16–AC-19 score against; `dropped.length` is exactly AC-18's denominator term.

## Architectural Constraints

- **Onion architecture, `server/`** (`onion-architecture` skill): the new `evals` module keeps the routes→service→repository shape (`server/AGENTS.md:19-21`). `repository.ts` is the only file in the module allowed to import `drizzle-orm`/`../../db/schema.js`. `service.ts` never imports Drizzle or Fastify types; it reaches other modules' data only via `Container` getters (`container.agentsRepo`, `container.reviewRepo`, `container.diffLoader`, `container.llm(provider)`) — never another module's `repository.ts` file directly, mirroring the container-getter convention documented at `platform/container.ts:111-113,143-148,239-244` and the "cross-module shared repositories" rule in the skill.
- **New module vs. extending `agents/`**: precedent is unambiguous — every prior cross-cutting spec-driven feature (`risk-brief/`, `blast/`) shipped as its **own** `modules/<name>/` plugin (own `routes.ts`+`service.ts`+`repository.ts`, registered once in `server/src/modules/index.ts:1-45`), constructing its service directly (`new XService(container)`) rather than adding a `Container` getter, exactly like `RiskBriefService`/`BlastService` (`risk-brief/routes.ts:33`, `blast/routes.ts:19`). `evals` follows the same shape: a new `server/src/modules/evals/` plugin owning `eval_cases`/`eval_runs`, registered as one new entry in `modules/index.ts`. This is the right call over extending `agents/` because: (a) one of its 7 routes (`POST /findings/:id/eval-case`) is finding/PR-scoped, not agent-scoped, so it doesn't belong in `agents/routes.ts` either; (b) `agents/repository.ts`/`service.ts` own `agents`/`agent_versions`/`agent_skills`/`agent_context_docs` — adding two more tables' worth of CRUD there would blur that module's existing ownership boundary the same way `risk-brief`'s own module comment explicitly rejected folding into `reviews/`.
- **Drizzle query patterns** (`drizzle-orm-patterns` skill): the batch-write for `POST /agents/:id/eval-runs`/`POST /agents/:id/eval-cases/:caseId/run` is one `db.transaction(async (tx) => tx.insert(t.evalRuns).values([...rows]).returning())` — a single multi-row `INSERT` is one statement, so every row's `defaultNow()` `ran_at` is identical by Postgres semantics; the explicit `db.transaction()` wrapper additionally satisfies the spec's own atomicity requirement (§5's failure contract: "Postgres unavailable mid-batch → the whole transaction rolls back"). Do **not** hold this transaction open across the (potentially many, slow) `reviewPullRequest` LLM calls — run + score every case first (sequential, per-case try/catch, AC-14), collect the resulting rows in memory, then do the one multi-row transactional insert at the end. Dashboard aggregation ("small aggregate over a short list") stays the established server idiom of an `IN`-query + JS `Map`/array grouping in `service.ts`, not a SQL `GROUP BY`/`sum()` (`server/INSIGHTS.md` 2026-08-04 entries, `pulls/routes.ts:114-186`) — batches are grouped by exact `ran_at` equality in JS, not SQL.
- **Zod** (`zod` skill): `EvalExpectation` and its `{ expectations: EvalExpectation[] }` wrapper get their own zod schema (exported type + schema, `type-export-schemas-and-types`). `eval_cases.expected_output`/`EvalCaseInput.expected_output` stay `z.unknown()` at the **route**-level Fastify schema (matching the existing, unmodified `EvalCaseInput` shape, `eval-ci.ts:20-29`) — the inner `{expectations: EvalExpectation[]}` shape is validated **inside the service** via `.safeParse()`, converting a failure into `ValidationError(message, issues)` (422, `platform/errors.ts:25-29`) per AC-10. This is a deliberate two-layer validation (`parse-validate-early` + `error-use-flatten`-style detail surfacing), not a gap — matching `agents/service.ts`'s own precedent of a service-level `ValidationError` beyond the route's Fastify schema (`agents/service.ts` `assertPathsAttachable`).
- **Fastify** (`fastify-best-practices` skill): every new route validates `params`/`body` via zod (`fastify-type-provider-zod`) exactly like `agents/routes.ts`/`risk-brief/routes.ts` — no hand-rolled `Schema.parse(req.body)` in a handler. Handlers stay thin (call service, shape response, throw `NotFoundError` on `undefined`), matching `agents/routes.ts:113-118`'s pattern.
- **Frontend UI architecture** (`frontend-ui-architecture` skill): all new data-fetching lives in one new `client/src/lib/hooks/evals.ts` file (one hook file per API domain, mirroring `lib/hooks/agents.ts`) — no inline `fetch`/`api.*` calls in components. New route-local components live under `<route>/_components/<Name>/` (component-folder anatomy: `.tsx`+`.test.tsx`+`index.ts`+colocated `constants.ts`/`helpers.ts`/`styles.ts` as needed). The one genuinely cross-route piece — `resolveAgentVersionForBatch(versions, ranAt)` (AC-22's client-side resolution) — is a pure function with exactly one real caller (the Compare view) at plan time; keep it colocated in the Compare view's own `helpers.ts` unless/until a second consumer appears, per the skill's "don't over-split" + "promote only once reused by 2+" guidance.
- **Non-default repo convention** (root `AGENTS.md:31-34`): `EvalExpectation` must be added to **both** `server/src/vendor/shared/contracts/` and `client/src/vendor/shared/contracts/` in the same Work Item — this hand-copied-twin split has already drifted before (`server/INSIGHTS.md`/`client/INSIGHTS.md`, both 2026-07-27 entries, `eval-ci.ts:144-172` vs the client copy).
- **No new pnpm workspace** (root `AGENTS.md` "no workspace tool" convention): the new root `package.json` (WI-9) must declare no `workspaces` field.
- **Shared agent-run-config resolution, not duplicated** (accepted revision to the original draft, which had `EvalsService` independently re-derive `ReviewRunExecutor.runOneAgent`'s config-resolution recipe inline): that duplication is a real long-term risk specific to this feature — if a future change to how a *real* review resolves an agent's effective config (provider/model/strategy/skill-filter/system-prompt assembly) isn't mirrored into the eval path, eval runs would silently stop reflecting the agent's actual current behavior, undermining the whole point of the harness (comparing real, current config). WI-6 now extracts this resolution into one shared function (`resolveAgentRunConfig`, target location `agents/helpers.ts` — confirm its exact current contents before placing it, since this plan hasn't re-read that file since drafting) that **both** `runOneAgent` and `EvalsService` call. This is the one deliberate exception to "reviews/ stays untouched": the edit to `run-executor.ts` must be a pure extraction (call the shared function instead of resolving inline) with **zero behavior change** for real reviews — `reviews/run-executor.test.ts` (or whichever test currently covers `runOneAgent`) must pass unchanged as proof.
