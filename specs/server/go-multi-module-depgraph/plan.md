## Context

`GoDepGraph.buildEdges()` (`server/src/adapters/depgraph/go.ts:31-78`) only ever reads `root/go.mod` via `readModulePath(root)` (`go.ts:81-88`), and if that single read fails, `buildEdges()` returns `[]` for *every* Go file in the repo (`go.ts:35-36`) — not just files under the missing module. Any multi-module monorepo (`go.mod` in subdirectories, none at root) or any single-module repo whose `go.mod` lives in a subdirectory gets zero Go edges, which collapses `rank.ts`'s PageRank to a flat uniform floor for every Go file (`server/src/modules/repo-intel/pipeline/rank.ts:22-23`'s documented behavior — a zero-edge graph gets graphology's own uniform distribution directly, not the `catch` fallback at `:39-47`, which only fires if `pagerank()` itself throws; cross-model review corrected this citation), and cascades into wrong Onboarding Generator output (confirmed empirically against two real repos in spec §1). This plan changes discovery from once-per-build (root only) to once-per-Go-file-directory (walk upward toward `root`), and fixes a co-located bug: `resolveLocalPackageDir()` (`go.ts:91-95`) returns a path relative to the module's *own* directory, but the caller looks it up directly against `filesByDir`'s *repo-relative* keys — today this coincidentally works only because the module dir is always `.` (root). Once modules can live anywhere, this needs an explicit join fix (AC-5/AC-6).

## Scope
- In scope: per-directory upward `go.mod` discovery (AC-1, AC-3, AC-4, AC-9, AC-11), per-module-independent local-import resolution for multi-module monorepos (AC-2), the repo-relative path-join fix for non-root modules (AC-5) with root-`go.mod` behavior preserved exactly (AC-6), per-file/per-module graceful degradation (AC-7, AC-8), and fail-closed map-lookup-only safety for traversal-shaped import paths (AC-10).

## Architectural Constraints
- `DepGraph` port signature (`buildEdges(root: string, files: string[]): Promise<FileEdge[]>`, `server/src/adapters/depgraph/index.ts:27-33`) must not change — this is an internal-algorithm change inside one existing adapter, not a new port or call-site contract (spec §10, confirmed by reading `index.ts:27-33`).
- `go.ts`'s module docstring states a "degrade that piece, don't fail the whole build" contract (`go.ts:18-20`) — must be preserved at the new, finer per-directory grain (per-directory/per-file degrade, not whole-build degrade), matching `DepCruiseGraph`'s existing try/catch-to-`[]` precedent (`index.ts:100-105`).
- `UnionDepGraph` composes `GoDepGraph` unchanged in its default builder array (`union.ts:16`) — no restructuring of `union.ts` or `index.ts` (spec §5, "no new external module boundary is introduced").
- `EXCLUDED_DIRS` (`node_modules`, `dist`, `build`, `coverage`, `.next`, `out`, `vendor`, `.git`) is defined at `server/src/modules/repo-intel/constants.ts:18-27` and applied at `pipeline/walk.ts:93`, before `GoDepGraph` ever sees the file list — the new upward discovery walk must not add its own exclusion logic (spec §4 Assumptions; cross-model review corrected the citation from `walk.ts:26-33`, which is only the import/`Set` construction, not the list itself).
- No new external dependency; extend only `go.ts`'s existing regex-based `MODULE_DIRECTIVE` parsing (`go.ts:28`) — no `require`/`replace`/`go`/`toolchain` directive parsing (spec §4 Constraints, §12).

## Work Items

1. **Add per-directory upward `go.mod` discovery with memoization** — implement a `discoverGoverningModule(root, dir, cache)` helper in `go.ts` that walks `dir` upward via repeated `dirname()` toward `root` (inclusive of `root` itself), checking for `go.mod` at each level, stopping at the first found or at `root`, never inspecting any path above `root`. **Existence check primitive (cross-model review flagged this as unspecified — now fixed): use `readFile` in a try/catch per candidate path, exactly mirroring the existing `readModulePath`'s own pattern (`go.ts:81-88`, try `readFile` → catch ENOENT → not found) — not a separate `stat`/`existsSync` call.** This gives AC-4/AC-9/AC-10's tests (Work Items 8/9, and the safety check in Work Item 5) a single, consistent fs call to assert against. Cache result (including "not found" as `null`) in a `Map<string, { modulePath: string; moduleDir: string } | null>` keyed by repo-relative directory, populated once per `buildEdges` call and reused for every directory lookup within that call (including repeat lookups from the discovery walk itself — a directory's own ancestors' results should also be cacheable to avoid re-reading a shared ancestor `go.mod` across sibling directories). Bound the walk strictly by path depth to `root` — no separate max-depth constant. — files: `server/src/adapters/depgraph/go.ts` — depends on: none — acceptance: walking upward from a directory 5+ segments deep with no `go.mod` anywhere terminates and returns `null` without hanging, checking at most one `readFile` call per directory level, never reading above `root` — satisfies: AC-1, AC-4, AC-9, AC-11

2. **Replace single root `readModulePath()` call with per-directory grouping + per-directory governing-module resolution** — restructure `buildEdges()`'s top of function: keep the existing `goFiles`/`filesByDir` grouping (`go.ts:32,38-44`), but remove the single `readModulePath(root)` call and its early `return []` (`go.ts:35-36`). Instead, for each directory that has Go files (from `filesByDir`'s keys, extended to also cover every directory reachable from Work Item 1's cache), resolve its governing module via Work Item 1's helper before attempting to read/parse any file in that directory. A directory whose governing-module lookup returns `null` produces no edges for its files but must not affect edge resolution for files in other directories with a governing `go.mod` (this is the finer-grain "degrade that piece" contract per `go.ts:18-20`). — files: `server/src/adapters/depgraph/go.ts` — depends on: Work Item 1 — acceptance: a mixed fixture (one directory under a real `go.mod`, one directory with no `go.mod` anywhere above it up to `root`) produces edges for the first directory's files and none for the second, without throwing — satisfies: AC-7

3. **Fix `resolveLocalPackageDir()` to return a module-relative path and join it with the governing `go.mod`'s own repo-relative directory at the call site** — per spec AC-5, `resolveLocalPackageDir(modulePath, importPath)` (`go.ts:91-95`) currently returns a path relative to the *module's own* directory (e.g. `internal/foo`), which the current caller looks up directly against `filesByDir`'s *repo-relative* keys — correct only when the module dir is `.` (root). Change the call site (inside the per-file edge-resolution loop, `go.ts:63-67`) to join the module-relative result with the governing module's own repo-relative directory (`moduleDir` from Work Item 1's cache entry) before using it as the `filesByDir` lookup key — e.g. `moduleDir === '.' ? pkgDir : join(moduleDir, pkgDir)` (normalize `.`/empty-segment edge cases so root behavior is unaffected). **Use Node's `path.join` for this (it normalizes `..` segments) — cross-model review clarified this against an earlier "pure string concatenation" phrasing that could be misread as suggesting a hand-rolled join; the safety property Work Item 5 relies on isn't "no normalization," it's "the joined string only ever feeds a `Map.get()`, never `path.resolve`/`fs.realpath`/a real filesystem call" — a `join`-normalized string that escapes `root`'s relative frame simply won't match any `filesByDir` key, so it fails closed regardless of `join`'s own normalization.** Do not change `resolveLocalPackageDir()`'s own external contract for the root case — when `moduleDir` is `.`, the joined result must equal today's bare `pkgDir` exactly (AC-6). — files: `server/src/adapters/depgraph/go.ts` — depends on: Work Item 1, Work Item 2 — acceptance: an import inside `gameserver/` (module `example.com/gameserver`) resolving to `example.com/gameserver/internal/foo` produces lookup key `gameserver/internal/foo`, not `internal/foo`; existing root-`go.mod` fixture (module `example.com/greeter`) continues to pass unmodified — satisfies: AC-5, AC-6

4. **Add a target-side governing-module guard (production code), closing a real cross-module-edge leak in nested-module layouts** — **cross-model review found the original test-only scoping of this Work Item insufficient; it now requires a real code change, not just a test.** Work Item 1's upward walk correctly makes deepest-`go.mod`-wins hold for the *source* file's own governing module (walk starts at the file's own directory, stops at the first `go.mod` found) — that half of AC-3 does fall out "for free." But nothing yet stops Work Item 3's join from producing a lookup key that lands inside a *different*, more-nested module's directory. Concrete failure case: outer `a/go.mod` (module `example.com/outer`) and inner `a/b/go.mod` (module `example.com/outer/b`) — a file directly in `a/` (governed by the outer module) that imports `example.com/outer/b/x` has `resolveLocalPackageDir` return `b/x` (a plain prefix match against the outer module's path string, blind to the inner module boundary), and Work Item 3's join produces repo-relative key `a/b/x` — a real bucket in `filesByDir`, silently creating an edge from an outer-module file into inner-module files. Under real Go semantics this import could never resolve as a same-module local import at all once `a/b/` declares its own `go.mod` (it would need a `require`/`replace`-based cross-module dependency — explicitly out of scope per spec §12) — so the correct behavior is **no edge**, not a wrong one. **Fix**: after Work Item 3 computes the joined repo-relative candidate directory, look up *that candidate's own* governing module via Work Item 1's memoized cache and compare it to the *source* file's own governing module (same `modulePath`/`moduleDir`); add the edge only if they match, skip (same as any other non-local import) if they differ or the candidate has no governing module. This is production code inside `go.ts`'s edge-resolution loop, not a verification-only addition. — files: `server/src/adapters/depgraph/go.ts`, `server/test/depgraph-go.test.ts` — depends on: Work Item 1, Work Item 2, Work Item 3 — acceptance: the outer/inner nested-module fixture above (a file in `a/` whose import string prefix-matches into `a/b/`) produces zero edges into `a/b/`'s files; a genuine same-module case (`a/` importing a subdirectory `a/sub/` that has no `go.mod` of its own, still governed by `a/go.mod`) continues to produce edges normally — satisfies: AC-3

5. **Preserve whole-repo empty-edges fallback and fail-closed traversal safety** — confirm (via Work Item 2's restructuring) that when *no* directory in the file set has any governing `go.mod`, `buildEdges` still returns `[]` for the whole build (every directory's discovery lookup returns `null`, so no directory ever attempts a read/parse) — this must fall out of Work Item 2's per-directory loop without a special-cased whole-repo check. Separately, confirm `resolveLocalPackageDir`'s output (post Work Item 3's join) is used strictly as a `Map.get()` key against `filesByDir` and never passed to `readFile`/`stat`/`join(root, ...)` as an actual filesystem path — an import resolving to a path with `../` segments must simply miss the map lookup (no matching directory bucket) rather than escape `root`. No filesystem safety code needs adding here as long as Work Item 3's `path.join` result feeds only a `Map` lookup and is never passed to `path.resolve`/`fs.realpath`/a real filesystem call — verify this property explicitly with a test rather than assuming it. — files: `server/src/adapters/depgraph/go.ts` (verification only, no new logic expected), `server/test/depgraph-go.test.ts` — depends on: Work Item 2, Work Item 3 — acceptance: existing "returns [] when go.mod is missing" test (`depgraph-go.test.ts:83-92`) continues to pass unmodified; new adversarial fixture with an import shaped like `example.com/gameserver/../../../etc` produces zero edges touching that import and no `readFile`/`stat` call for any path outside `root` — satisfies: AC-8, AC-10
